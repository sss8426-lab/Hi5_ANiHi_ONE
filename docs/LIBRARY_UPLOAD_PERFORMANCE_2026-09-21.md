# 자료보관함 업로드 처리 개선

## 변경 범위

- 원본 업로드와 로컬 480px WebP 미리보기 준비를 동시에 시작한다.
- 대형 이미지 decode/encode는 한 장씩 처리하지만 미리보기 서버 응답은 해당 메모리 제한을 점유하지 않는다.
- 기존 파일 작업 동시 실행 상한 3개와 대용량 multipart 제한은 유지한다. 무제한 병렬 업로드가 아니다.
- 원본 저장에 성공한 파일에만 미리보기를 연결한다. 미리보기 저장에는 15초 제한을 두고 실패해도 원본 성공을 유지한다.
- 업로드 창에 `원본 저장 완료 · 미리보기 준비 중` 단계를 구분한다.
- 서버는 자료보관함에서 검증한 multipart FormData를 공통 업로드 함수로 전달한다. 같은 파일의 재직렬화/재파싱을 제거하되 기존 인증, 캠퍼스, 폴더 및 private 검사는 모두 유지한다.

## 데이터 보존

원본 File bytes, 원본 파일명, 기존 폴더/file ID 및 R2 저장 규칙은 변경하지 않는다.
스키마/migration, 운영 데이터 변환, 계정 변경, R2 삭제 또는 공개 URL 추가는 없다.
PSD/AI 등 디자인 원본은 기존 전송 경로를 사용하고 이미지 decode를 시도하지 않는다.

## 검증

- `tests/library-upload-pipeline.test.mjs`: 8장 처리, 최대 3개 작업, 단일 decode, 업로드/encode 중첩, 원본 실패 후 재사용, 썸네일 실패/timeout/cancel 시 원본 보존.
- `scripts/library-browser-smoke.mjs`: 실제 브라우저와 빌드된 Worker, 임시 합성 D1/R2에서 8장 업로드, 모든 원본 bytes 비교, 썸네일 연결, 권한 및 파일 관리 회귀. 1920/1440/1024/820/390/320px 검사.
- `scripts/check-library-upload-performance.mjs`: 실제 Chrome 이미지 decode/encode, 3200x2400 합성 JPEG 8장. 원본 응답 100ms, 미리보기 응답 250ms를 고정한 비교에서 이전 2619ms, 변경 후 1082ms(약 59% 감소). 기준 commit은 `b70c8b7e78146d4ec2ce0ff8a3c8837a8eeac207`.

위 시간은 고정 지연을 넣은 로컬 비교값이다. 운영 업로드 속도 개선율이나 인터넷 대역폭 측정값으로 해석하면 안 된다. 실제 속도는 원본 크기, 기기, 네트워크 및 서버 응답에 따라 달라진다.
브라우저 harness의 `--preview`는 배포된 정적 자산 동일성을 확인하며, 업로드/수정 검증은 항상 격리된 합성 DB/R2에서만 실행한다. 운영 실제 파일을 테스트로 업로드하거나 변경하지 않는다.

## 남은 제약

미리보기가 실패하면 원본을 그대로 사용하므로 해당 목록의 초기 이미지 다운로드는 상대적으로 클 수 있다. 이번 작업은 원본의 해상도/품질을 낮추지 않는다.
기존 ESLint 경고와 의존성 audit는 업로드 개선과 분리하며 강제 의존성 업데이트는 하지 않는다.
